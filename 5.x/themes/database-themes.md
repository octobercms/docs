# Storing Themes in the Database

Database templates store every change to CMS templates in the database instead of the filesystem. Use them when you can't write to the filesystem, or when the website runs on several servers that need to see the same edits. They cover pages, layouts, partials, content files and language files.

```text
CMS_DB_TEMPLATES=true
```

## Enabling Database Templates

To enable the feature for all themes, set the `cms.database_templates` config item, or the `CMS_DB_TEMPLATES` environment variable shown above.

To enable it for a single theme, go to **Settings → Site Theme**, select **Manage → Edit Properties** for the theme, and check **Database Mode** on the **Advanced** tab.

## How Database Templates Work

When the database layer is active for a theme, edits made in the CMS editor are written to the database instead of the filesystem. Reads check the database first and fall back to the filesystem, so files that have never been edited are still served directly from the theme directory.

Deleting a template in the editor writes a tombstone row to the database. The tombstone hides the filesystem copy from listings and reads, so the file appears deleted on every instance, even though the copy on disk is still present. Language files use the same mechanism.

## Exporting Changes to the Filesystem

The `theme:copy` command with the `--import-db` option copies the database version of the theme to the filesystem. It imports templates, language files, assets and blueprints in a single pass, and applies tombstones by deleting the matching files on disk.

```bash
php artisan theme:copy demo --import-db
```

Add the `--purge-db` option to delete the imported database rows at the same time.

```bash
php artisan theme:copy demo --import-db --purge-db
```

## Storing Assets in Shared Storage

By default, asset files such as images and stylesheets are not saved in the database, and you can't change them without access to the filesystem. When your application runs on multiple instances with a disposable local filesystem, asset edits made in the CMS editor (theme CSS, JavaScript, images and fonts) need a shared place to live. Database-driven assets publish these files to a shared storage disk, so every instance sees them immediately.

::: aside
This feature is intended for multi-instance deployments where the local filesystem cannot be relied on. For single-instance setups, the default filesystem behavior is simpler and recommended.
:::

### How It Works

Theme assets are published to a dedicated `assets` filesystem disk. In production, this disk is usually backed by Amazon S3 or another object storage service, with a CDN in front. The `ASSET_URL` environment variable points at the same origin, so URLs generated by `asset()` resolve to the published location.

When an asset is edited in the admin panel, the new file is written directly to the `assets` disk and a database record tracks the change. The edit is live on every instance immediately.

### Setting Up Shared Asset Storage

The feature needs three pieces in place.

**1. Configure the `assets` filesystem disk**

Add an `assets` disk to your **config/filesystems.php** file. For an S3-backed setup:

```php
'assets' => [
    'driver' => 's3',
    'key' => env('AWS_ACCESS_KEY_ID'),
    'secret' => env('AWS_SECRET_ACCESS_KEY'),
    'region' => env('AWS_DEFAULT_REGION'),
    'bucket' => env('AWS_ASSETS_BUCKET'),
    'url' => env('ASSET_URL'),
    'visibility' => 'public',
],
```

For local development, you can point the disk at a public path on the local filesystem instead.

**2. Set the `ASSET_URL` environment variable**

Point `ASSET_URL` at the same origin as the `assets` disk, so that `asset()` calls resolve to the published location.

```text
ASSET_URL=https://cdn.example.com
```

**3. Enable the feature**

Set the `cms.database_assets` config item, or the environment variable.

```text
CMS_DB_ASSETS=true
```

The feature is disabled by default, so a fresh checkout of the project runs without shared storage credentials.

### Publishing Assets on Deployment

The `october:mirror` command with the `--disk` option publishes all theme, module, plugin and app assets to a filesystem disk. Run it in your deployment pipeline so the published assets match the latest version of the code.

```bash
php artisan october:mirror --disk=assets
```

The command is additive: it uploads or overwrites files but never deletes them. You can clean up files orphaned by code changes with lifecycle rules on the storage bucket. Unchanged files are skipped by comparing their sizes. The following options change this behavior.

- `--checksum` compares content hashes instead of sizes.
- `--force` uploads every file.
- `--dry-run` lists the files that would be uploaded without uploading them.

### Clearing the CDN Cache

When an asset changes in the CMS editor, the `cms.asset.invalidate` event fires with the theme and the changed disk paths. The core stays CDN-agnostic, so listen to this event to purge the cached copies at your CDN.

```php
Event::listen('cms.asset.invalidate', function ($theme, $diskPaths) {
    MyCdnProvider::invalidate($diskPaths);
});
```
