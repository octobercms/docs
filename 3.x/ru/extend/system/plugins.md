# Плагины

::: aside
Плагины идентифицируются уникальным кодом, например, плагин `Acme.Blog` находится в директории **plugins/acme/blog**.
:::

В этой статье описываются плагины и их функции регистрации. Процесс регистрации позволяет плагинам объявлять свои функции, такие как CMS-компоненты или навигацию и страницы панели управления. Вот некоторые примеры того, что может делать плагин.

1. Создавать структуры таблиц базы данных и начальные данные.
1. Определять [CMS-компоненты](../cms-components.md).
1. Определять [пользовательские разрешения](../backend/permissions.md).
1. Добавлять [страницы настроек](../settings/settings.md), [элементы навигации](../backend/navigation.md), [списки](../lists/list-controller.md) и [формы](../forms/form-controller.md).
1. Изменять [функциональность ядра или других плагинов](../extending.md).
1. Предоставлять классы, [контроллеры панели управления](../system/controllers.md), представления, ресурсы и другие файлы.

### Структура директории

Плагины находятся в директории **plugins** директории приложения. Пример структуры директории плагина приведён ниже.

::: dir
├── `plugins`
|   └── acme  _← Имя автора_
|       └── blog  _← Имя плагина_
|           ├── classes
|           ├── components
|           ├── controllers
|           ├── models
|           ├── updates
|           └── Plugin.php  _← Файл регистрации_
:::

Не все директории плагина обязательны. Единственный обязательный файл — **Plugin.php**, описанный ниже. Если ваш плагин предоставляет только один компонент, структура директории плагина может быть гораздо проще, например:

::: dir
├── plugins
|   └── acme
|       └── blog
|           ├── `components`
|           └── Plugin.php
:::

### Пространства имён плагинов

Пространства имён плагинов необходимы, особенно если вы планируете публиковать плагины на [маркетплейсе October CMS](https://octobercms.com/plugins). При регистрации в качестве автора на маркетплейсе вам будет предложено указать код автора, который должен использоваться как корневое пространство имён для всех ваших плагинов. Код автора можно указать только один раз при регистрации. Код автора по умолчанию, предлагаемый маркетплейсом, состоит из имени и фамилии автора: JohnSmith. Код нельзя изменить после регистрации. Все пространства имён ваших плагинов должны быть определены под корневым пространством имён, например `JohnSmith\Blog`.

## Файл регистрации

Команда `create:plugin` генерирует папку плагина и базовые файлы. Первый аргумент указывает имя автора и плагина.

```bash
php artisan create:plugin Acme.Blog
```

Файл **Plugin.php**, называемый файлом регистрации плагина, является скриптом инициализации, объявляющим основные функции и информацию плагина. Файлы регистрации могут предоставлять следующее:

1. Информацию о плагине, его название и автора.
1. Методы регистрации для расширения CMS.

Скрипты регистрации должны использовать пространство имён плагина. Скрипт регистрации должен определять класс с именем `Plugin`, наследующий класс `System\Classes\PluginBase`. Единственный обязательный метод класса регистрации плагина — `pluginDetails`. Пример файла регистрации плагина приведён ниже.

```php
namespace Acme\Blog;

class Plugin extends \System\Classes\PluginBase
{
    public function pluginDetails()
    {
        return [
            'name' => 'Blog Plugin',
            'description' => 'Provides some really cool blog features.',
            'author' => 'ACME Corporation',
            'icon' => 'icon-leaf'
        ];
    }

    public function registerComponents()
    {
        return [
            \Acme\Blog\Components\Post::class => 'blogPost'
        ];
    }
}
```

### Базовая информация о плагине

Метод `pluginDetails` является обязательным методом класса регистрации плагина. Он должен возвращать массив, содержащий следующие ключи:

Ключ | Описание
------------- | -------------
**name** | название плагина, обязательно.
**description** | описание плагина, обязательно.
**author** | имя автора плагина, обязательно.
**icon** | имя иконки плагина. Полный список доступных иконок можно найти в [документации по доступным иконкам](../../element/available-icons.md). Любые имена иконок, предоставляемые этим шрифтом, являются допустимыми, например **icon-glass**, **icon-music**, необязательно.
**iconSvg** | SVG-иконка, используемая вместо стандартной иконки. SVG-иконка должна быть прямоугольной и может поддерживать цвета, необязательно.
**homepage** | ссылка на веб-сайт автора, необязательно.
**hint** | более короткий код, используемый для [маршрутизации URL контроллеров](./controllers.md) в панели управления, необязательно.

## Загрузка и инициализация

Файлы регистрации плагинов могут содержать два метода `boot` и `register`. С помощью этих методов вы можете делать всё что угодно, например регистрировать маршруты или подключать обработчики событий.

Метод `register` вызывается сразу при регистрации плагина. Метод `boot` вызывается непосредственно перед маршрутизацией запроса. Поэтому, если ваши действия зависят от другого плагина, используйте метод boot. Например, внутри метода `boot` можно расширять модели.

```php
public function boot()
{
    User::extend(function($model) {
        $model->hasOne['author'] = \Acme\Blog\Models\Author::class;
    });
}
```

::: tip
Метод `boot` является необязательным, и его отсутствие улучшает производительность. Кроме того, только метод `boot` поддерживает внедрение зависимостей через контейнер приложения.
:::

Плагины также могут предоставлять файл **init.php**, содержащий пользовательскую логику инициализации. Ниже приведён пример содержимого.

```php
App::before({
    // Logic when the request starts, after routes are registered
});

App::after({
    // Logic the request has finished, after the response is sent
});
```

## Определение зависимостей

Плагин может зависеть от других плагинов, определив свойство `$require` в файле регистрации плагина. Свойство должно содержать массив имён плагинов, которые считаются зависимостями. Плагин, зависящий от плагина **Acme.User**, может объявить эту зависимость следующим образом:

```php
namespace Acme\Blog;

class Plugin extends \System\Classes\PluginBase
{
    /**
     * @var array require these plugins
     */
    public $require = ['Acme.User'];

    // ...
}
```

Определения зависимостей влияют на работу плагина и на то, как процесс обновления применяет миграции. Процесс установки попытается установить все зависимости автоматически, однако если плагин обнаружен в системе без каких-либо своих зависимостей, он будет отключён для предотвращения системных ошибок.

Определения зависимостей могут быть сложными, но следует избегать циклических ссылок. Граф зависимостей всегда должен быть направленным, а циклическая зависимость считается ошибкой проектирования.

## История версий

Хорошей практикой для плагинов является ведение журнала изменений, документирующего любые изменения или улучшения в коде. Помимо написания заметок об изменениях, этот процесс обладает полезной возможностью выполнять [файлы миграций и заполнения](../database/structure.md) в правильном порядке.

Журнал изменений хранится в YAML-файле `version.yaml` внутри директории **updates** плагина, который соседствует с файлами миграций и заполнения. Этот пример показывает типичную структуру директории обновлений плагина:

::: dir
├── plugins
|   └── author
|       └── myplugin
|           ├── `updates`
|           |   ├── `version.yaml`  _← Файл версий_
|           |   ├── create_tables.php  _← Скрипт базы данных_
|           |   ├── seed_the_database.php
|           |   └── create_another_table.php
|           └── Plugin.php
:::

### Зависимости плагинов

Обновления применяются в определённом порядке, основанном на зависимостях, определённых в файле регистрации плагина. Зависимые плагины не будут обновляться, пока все их зависимости не будут обновлены первыми.

```php
namespace Acme\Blog;

class Plugin extends \System\Classes\PluginBase
{
    public $require = ['Acme.User'];
}
```

В приведённом выше примере плагин **Acme.Blog** не будет обновлён, пока плагин **Acme.User** не будет полностью обновлён.

## Файл версий плагина

Файл **version.yaml**, называемый файлом версий плагина, содержит комментарии к версиям и ссылается на скрипты базы данных в правильном порядке. Пожалуйста, прочитайте статью [Структура базы данных](../database/structure.md) для получения информации о файлах миграций. Этот файл обязателен, если вы собираетесь отправить плагин на [маркетплейс](https://octobercms.com/help/site/marketplace). Вот пример файла версий плагина.

```yaml
v1.0.1: First version
v1.0.2: Second version
v1.0.3:
    - Update with a migration and seed
    - create_tables.php
    - seed_the_database.php
v2.0.0: Important update
v2.0.1: Latest version
```

::: tip
Файл `version.yaml` должен всегда использовать первую строку для текстового обновления, описывающего изменения, а оставшиеся строки — для скриптов обновления. Для более подробных обновлений рассмотрите использование отдельного файла журнала изменений.
:::

Как видно выше, должен быть ключ, представляющий номер версии, за которым следует сообщение обновления — строка или массив, содержащий сообщения обновления. Для обновлений, ссылающихся на файлы миграций или заполнения, строки с именами файлов скриптов могут располагаться в любой позиции. Пример комментария без связанных файлов обновления.

```yaml
v1.0.1: A single comment that uses no update scripts.
```

### Важные обновления

Иногда плагину необходимо внести изменения, которые сломают сайты, уже использующие плагин. Чтобы предотвратить автоматическое развёртывание изменений, следует увеличить **мажорный** сегмент строки версии (`major.minor.patch`). Пример комментария важного обновления приведён ниже.

```yaml
v2.1.0: This is an important update from v1 that contains breaking changes.
```

При тегировании новой версии `v2` с версии `v1` изменения не развёртываются в рамках обычного обновления. Пользователь должен установить плагин заново, чтобы получить последнюю версию через Composer.

### Файлы миграций и заполнения

Как было описано ранее, обновления также определяют, когда должны применяться [файлы миграций и заполнения](../database/structure.md). Строка обновления с комментарием и обновлениями:

```yaml
v1.1.1:
    - This update will execute the two scripts below.
    - some_upgrade_file.php
    - some_seeding_file.php
```

Имя файла обновления должно использовать *snake_case*, а содержащийся PHP-класс — *CamelCase*. Для файла с именем **some_upgrade_file.php** соответствующий класс будет `SomeUpgradeFile`.

```php
<?php namespace Acme\Blog\Updates;

use Schema;
use October\Rain\Database\Updates\Migration;

/**
 * some_upgrade_file.php
 */
class SomeUpgradeFile extends Migration
{
    ///
}
```
