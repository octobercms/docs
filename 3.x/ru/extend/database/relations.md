# Связи

Таблицы базы данных часто связаны друг с другом. Например, запись блога может иметь много комментариев, или заказ может быть связан с пользователем, который его разместил. October CMS упрощает управление и работу с этими связями и поддерживает несколько различных типов связей.

## Определение связей

Связи модели определяются как свойства в классах моделей. Пример определения связей:

```php
class User extends Model
{
    public $hasMany = [
        'posts' => \Acme\Blog\Models\Post::class
    ]
}
```

Связи, как и сами модели, также служат мощными [конструкторами запросов](./query.md), и доступ к связям как к функциям предоставляет мощные возможности для построения цепочек методов и запросов. Например:

```php
$user->posts()->where('is_active', true)->get();
```

Доступ к связи как к свойству также возможен.

```php
$user->posts;
```

## Детальные определения

Каждое определение может быть массивом, где ключ — это имя связи, а значение — массив деталей. Первое значение массива деталей — всегда имя класса связанной модели, а все остальные значения являются параметрами, которые должны иметь именованный ключ.

```php
public $hasMany = [
    'posts' => [\Acme\Blog\Models\Post::class, 'delete' => true]
];
```

Ниже перечислены параметры, которые могут использоваться со всеми связями:

Аргумент | Описание
------------- | -------------
**order** | порядок сортировки для нескольких записей.
**conditions** | фильтрует связь с помощью необработанного оператора where.
**scope** | фильтрует связь с помощью метода [области запроса модели](../database/model.md).
**push** | если установлено в `false`, эта связь не будет сохранена через метод `push`. По умолчанию: `true`
**delete** | если установлено в `true`, связанная модель будет удалена при удалении основной модели или разрушении связи. По умолчанию: `false`
**softDelete** | если установлено в `true`, связанная модель будет мягко удалена при [мягком удалении основной модели](./traits.md). По умолчанию: `false`
**replicate** | если установлено в true, связанная модель будет дублирована или ассоциирована через метод `replicate`. По умолчанию: `false`.
**relationClass** | указывает пользовательское имя класса для связанного объекта.

Пример фильтрации с использованием параметров `order` и `conditions`.

```php
public $belongsToMany = [
    'categories' => [
        \Acme\Blog\Models\Category::class,
        'order' => 'name desc',
        'conditions' => 'is_active = 1'
    ]
];
```

Пример фильтрации с использованием параметра `scope`.

```php
class Post extends Model
{
    public $belongsToMany = [
        'categories' => [
            \Acme\Blog\Models\Category::class,
            'scope' => 'isActive'
        ]
    ];
}

class Category extends Model
{
    public function scopeIsActive($query)
    {
        return $query->where('is_active', true)->orderBy('name', 'desc');
    }
}
```

Параметр `scope` также может ссылаться на статический метод.

```php
public $belongsToMany = [
    'categories' => [
        \Acme\Blog\Models\Category::class,
        'scope' => [self::class, 'myFilterMethod']
    ]
];

public static function myFilterMethod($query, $related, $parent)
{
    // ...
}
```

Пример реализации с использованием параметра `relationClass`.

```php
public $belongsToMany = [
    'users' => [
        \Backend\Models\User::class,
        'relationClass' => \Backend\Classes\MyBelongsToMany::class
    ]
];
```

::: tip
`relationClass` должен наследовать класс указанного типа. Например, при использовании `belongsTo` класс должен наследовать `October\Rain\Database\Relations\BelongsTo`.
:::

<a id="relation-one-to-one"></a>
### Один к одному

Связь один к одному — это очень базовая связь. Например, модель `User` может быть связана с одним `Phone`. Для определения этой связи мы добавляем запись `phone` в свойство `$hasOne` модели `User`.

```php
namespace Acme\Blog\Models;

use Model;

class User extends Model
{
    public $hasOne = [
        'phone' => \Acme\Blog\Models\Phone::class
    ];
}
```

После определения связи мы можем получить связанную запись, используя свойство модели с тем же именем. Эти свойства являются динамическими и позволяют обращаться к ним, как если бы они были обычными атрибутами модели.

```php
$phone = User::find(1)->phone;
```

Модель предполагает внешний ключ связи на основе имени модели. В этом случае модель `Phone` автоматически предполагается имеющей внешний ключ `user_id`. Если вы хотите переопределить это соглашение, вы можете передать параметр `key` в определение.

```php
public $hasOne = [
    'phone' => [\Acme\Blog\Models\Phone::class, 'key' => 'my_user_id']
];
```

Кроме того, модель предполагает, что внешний ключ должен иметь значение, совпадающее со столбцом `id` родителя. Другими словами, она будет искать значение столбца `id` пользователя в столбце `user_id` записи `Phone`. Если вы хотите, чтобы связь использовала значение, отличное от `id`, вы можете передать параметр `otherKey` в определение:

```php
public $hasOne = [
    'phone' => [\Acme\Blog\Models\Phone::class, 'key' => 'my_user_id', 'otherKey' => 'my_id']
];
```

#### Определение обратной связи

Теперь, когда мы можем получить доступ к модели `Phone` из нашего `User`, давайте сделаем обратное и определим связь на модели `Phone`, которая позволит нам получить доступ к `User`, владеющему телефоном. Мы можем определить обратную сторону связи `hasOne`, используя свойство `$belongsTo`:

```php
class Phone extends Model
{
    public $belongsTo = [
        'user' => \Acme\Blog\Models\User::class
    ];
}
```

В приведённом выше примере модель попытается сопоставить `user_id` из модели `Phone` с `id` модели `User`. Она определяет имя внешнего ключа по умолчанию, анализируя имя определения связи и добавляя суффикс `_id`. Однако, если внешний ключ в модели `Phone` не является `user_id`, вы можете передать пользовательское имя ключа с помощью параметра `key` в определении:

```php
public $belongsTo = [
    'user' => [Acme\Blog\Models\User::class, 'key' => 'my_user_id']
];
```

Если ваша родительская модель не использует `id` в качестве первичного ключа, или вы хотите присоединить дочернюю модель к другому столбцу, вы можете передать параметр `otherKey` в определение, указывающий пользовательский ключ родительской таблицы:

```php
public $belongsTo = [
    'user' => [\Acme\Blog\Models\User::class, 'key' => 'my_user_id', 'otherKey' => 'my_id']
];
```

#### Модели по умолчанию

Связь `belongsTo` позволяет определить модель по умолчанию, которая будет возвращена, если данная связь равна `null`. Этот паттерн часто называют [паттерном Null Object](https://en.wikipedia.org/wiki/Null_Object_pattern), и он помогает убрать условные проверки из вашего кода. В следующем примере связь `user` вернёт пустую модель `Acme\Blog\Models\User`, если ни один `user` не прикреплён к посту.

```php
public $belongsTo = [
    'user' => [\Acme\Blog\Models\User::class, 'default' => true]
];
```

Для заполнения модели по умолчанию атрибутами вы можете передать массив в параметр `default`.

```php
public $belongsTo = [
    'user' => [
        \Acme\Blog\Models\User::class,
        'default' => ['name' => 'Guest']
    ]
];
```

<a id="relation-one-to-many"></a>
### Один ко многим

Связь один ко многим используется для определения связей, где одна модель владеет любым количеством других моделей. Например, запись блога может иметь бесконечное количество комментариев. Как и все другие связи, связи один ко многим определяются добавлением записи в свойство `$hasMany` вашей модели:

```php
class Post extends Model
{
    public $hasMany = [
        'comments' => \Acme\Blog\Models\Comment::class
    ];
}
```

Помните, модель автоматически определит правильный столбец внешнего ключа в модели `Comment`. По соглашению, она возьмёт имя владеющей модели в формате «snake case» и добавит суффикс `_id`. Таким образом, для этого примера мы можем предположить, что внешний ключ в модели `Comment` — это `post_id`.

После определения связи мы можем получить доступ к коллекции комментариев, обращаясь к свойству `comments`. Помните, поскольку модель предоставляет «динамические свойства», мы можем обращаться к связям, как если бы они были определены как свойства модели:

```php
$comments = Post::find(1)->comments;

foreach ($comments as $comment) {
    //
}
```

Конечно, поскольку все связи также служат конструкторами запросов, вы можете добавлять дополнительные ограничения к тому, какие комментарии извлекаются, вызывая метод `comments` и продолжая цепочку условий запроса:

```php
$comments = Post::find(1)->comments()->where('title', 'foo')->first();
```

Как и в связи `hasOne`, вы также можете переопределить внешний и локальный ключи, передав параметры `key` и `otherKey` в определение соответственно:

```php
public $hasMany = [
    'comments' => [\Acme\Blog\Models\Comment::class, 'key' => 'my_post_id', 'otherKey' => 'my_id']
];
```

#### Определение обратной связи

Теперь, когда мы можем получить доступ ко всем комментариям поста, давайте определим связь, позволяющую комментарию получить доступ к его родительскому посту. Для определения обратной стороны связи `hasMany` определите свойство `$belongsTo` в дочерней модели:

```php
class Comment extends Model
{
    public $belongsTo = [
        'post' => \Acme\Blog\Models\Post::class
    ];
}
```

После определения связи мы можем получить модель `Post` для `Comment`, обращаясь к динамическому свойству `post`:

```php
$comment = Comment::find(1);

echo $comment->post->title;
```

В приведённом выше примере модель попытается сопоставить `post_id` из модели `Comment` с `id` модели `Post`. Она определяет имя внешнего ключа по умолчанию, анализируя имя связи и добавляя суффикс `_id`. Однако, если внешний ключ в модели `Comment` не является `post_id`, вы можете передать пользовательское имя ключа с помощью параметра `key`:

```php
public $belongsTo = [
    'post' => [\Acme\Blog\Models\Post::class, 'key' => 'my_post_id']
];
```

Если ваша родительская модель не использует `id` в качестве первичного ключа, или вы хотите присоединить дочернюю модель к другому столбцу, вы можете передать параметр `otherKey` в определение, указывающий пользовательский ключ родительской таблицы:

```php
public $belongsTo = [
    'post' => [Acme\Blog\Models\Post::class, 'key' => 'my_post_id', 'otherKey' => 'my_id']
];
```

<a id="relation-many-to-many"></a>
### Многие ко многим

Связи многие ко многим несколько сложнее, чем связи `hasOne` и `hasMany`. Примером такой связи является пользователь с множеством ролей, где роли также разделяются другими пользователями. Например, многие пользователи могут иметь роль «Администратор». Для определения этой связи необходимы три таблицы базы данных: `users`, `roles` и `role_user`. Таблица `role_user` образуется из алфавитного порядка имён связанных моделей и содержит столбцы `user_id` и `role_id`.

Ниже приведён пример, показывающий [структуру таблицы базы данных](./structure.md), используемую для создания связующей таблицы.

```php
Schema::create('role_user', function($table) {
    $table->integer('user_id')->unsigned();
    $table->integer('role_id')->unsigned();
    $table->primary(['user_id', 'role_id']);
});
```

Связи многие ко многим определяются добавлением записи в свойство `$belongsToMany` класса модели. Например, определим связь `roles` в нашей модели `User`:

```php
class User extends Model
{
    public $belongsToMany = [
        'roles' => \Acme\Blog\Models\Role::class
    ];
}
```

После определения связи вы можете получить доступ к ролям пользователя, используя динамическое свойство `roles`:

```php
$user = User::find(1);

foreach ($user->roles as $role) {
    //
}
```

Конечно, как и все другие типы связей, вы можете вызвать метод `roles` для продолжения цепочки ограничений запроса к связи:

```php
$roles = User::find(1)->roles()->orderBy('name')->get();
```

Как упоминалось ранее, для определения имени таблицы связующей таблицы связи модель объединяет два имени связанных моделей в алфавитном порядке. Однако вы можете переопределить это соглашение. Вы можете сделать это, передав параметр `table` в определение `belongsToMany`:

```php
public $belongsToMany = [
    'roles' => [\Acme\Blog\Models\Role::class, 'table' => 'acme_blog_role_user']
];
```

Помимо настройки имени связующей таблицы, вы также можете настроить имена столбцов ключей в таблице, передав дополнительные параметры в определение `belongsToMany`. Параметр `key` — это имя внешнего ключа модели, в которой вы определяете связь, а параметр `otherKey` — это имя внешнего ключа модели, к которой вы присоединяетесь:

```php
public $belongsToMany = [
    'roles' => [
        \Acme\Blog\Models\Role::class,
        'table' => 'acme_blog_role_user',
        'key' => 'my_user_id',
        'otherKey' => 'my_role_id'
    ]
];
```

#### Определение обратной связи

Для определения обратной стороны связи многие ко многим вы просто помещаете ещё одно свойство `$belongsToMany` в связанную модель. Продолжая наш пример с ролями пользователей, определим связь `users` в модели `Role`:

```php
class Role extends Model
{
    public $belongsToMany = [
        'users' => \Acme\Blog\Models\User::class
    ];
}
```

Как видите, связь определена точно так же, как её аналог в `User`, за исключением простой ссылки на модель `Acme\Blog\Models\User`. Поскольку мы повторно используем свойство `$belongsToMany`, все обычные параметры настройки таблицы и ключей доступны при определении обратной стороны связей многие ко многим.

#### Получение столбцов промежуточной таблицы

Как вы уже знаете, работа со связями многие ко многим требует наличия промежуточной связующей таблицы. Модели предоставляют несколько очень полезных способов взаимодействия с этой таблицей. Например, предположим, что наш объект `User` имеет много объектов `Role`, с которыми он связан. После доступа к этой связи мы можем обратиться к промежуточной таблице, используя атрибут `pivot` моделей:

```php
$user = User::find(1);

foreach ($user->roles as $role) {
    echo $role->pivot->created_at;
}
```

Обратите внимание, что каждой модели `Role`, которую мы получаем, автоматически назначается атрибут `pivot`. Этот атрибут содержит модель, представляющую промежуточную таблицу, и может использоваться как любая другая модель.

По умолчанию только ключи модели будут присутствовать в объекте `pivot`. Если ваша сводная таблица содержит дополнительные атрибуты, вы должны указать их при определении связи:

```php
public $belongsToMany = [
    'roles' => [
        \Acme\Blog\Models\Role::class,
        'pivot' => ['column1', 'column2']
    ]
];
```

Если вы хотите, чтобы ваша сводная таблица имела автоматически поддерживаемые временные метки `created_at` и `updated_at`, используйте параметр `timestamps` в определении связи:

```php
public $belongsToMany = [
    'roles' => [
        \Acme\Blog\Models\Role::class,
        'timestamps' => true
    ]
];
```

Если вы хотите определить пользовательскую модель для представления промежуточной таблицы вашей связи, вы можете использовать атрибут `pivotModel` при определении связи. Пользовательские сводные модели многие ко многим должны наследовать класс `October\Rain\Database\Pivot`, а пользовательские полиморфные сводные модели многие ко многим должны наследовать класс `October\Rain\Database\MorphPivot`.

```php
public $belongsToMany = [
    'roles' => [
        \Acme\Blog\Models\Role::class,
        'pivotModel' => \Acme\Blog\Models\UserRolePivot::class
    ]
];
```

#### Разрешение дублирующихся связей

В некоторых случаях вы можете захотеть ассоциировать одну и ту же связь дважды или более, используя различные данные сводной таблицы для каждой прикреплённой записи. Ниже приведён пример, показывающий [структуру таблицы базы данных](./structure.md) с автоинкрементным первичным ключом в связующей таблице вместо составного первичного ключа.

```php
Schema::create('role_user', function($table) {
    $table->increments('id');
    $table->integer('user_id')->unsigned();
    $table->integer('role_id')->unsigned();
});
```

Для этой конфигурации необходимо использовать пользовательскую `pivotModel`, а свойство `pivotKey` устанавливается в имя автоинкрементного столбца (`id`).

```php
public $belongsToMany = [
    'roles' => [
        \Acme\Blog\Models\Role::class,
        'pivotModel' => \Acme\Blog\Models\UserRolePivot::class,
        'pivotKey' => 'id'
    ]
];
```

Определение сводной модели должно устанавливать свойство `$incrementing` в `true` для включения автоинкрементного первичного ключа, который по умолчанию имеет значение `id`, как и любая другая модель.

```php
class UserRolePivot extends \October\Rain\Database\Pivot
{
    public $incrementing = true;
}
```

Ниже перечислены свойства, поддерживаемые для связей `belongsToMany`:

Свойство | Описание
------------- | -------------
**table** | имя связующей таблицы.
**key** | имя столбца ключа определяющей модели (внутри сводной таблицы). Значение по умолчанию составляется из имени модели и суффикса `_id`, например `user_id`
**parentKey** | имя столбца ключа определяющей модели (внутри таблицы определяющей модели). По умолчанию: id
**otherKey** | имя столбца ключа связанной модели (внутри сводной таблицы). Значение по умолчанию составляется из имени модели и суффикса `_id`, например `role_id`
**relatedKey** | имя столбца ключа связанной модели (внутри таблицы связанной модели). По умолчанию: id
**timestamps** | если true, связующая таблица должна содержать столбцы `created_at` и `updated_at`. По умолчанию: `false`
**detach** | если установлено в false, связанная модель не будет отсоединена при удалении основной модели или разрушении связи. По умолчанию: true.
**pivot** | массив сводных столбцов, находящихся в связующей таблице, атрибуты доступны через `$model->pivot`.
**pivotModel** | указывает пользовательский класс модели для возврата при доступе к сводной связи. По умолчанию: `October\Rain\Database\Pivot`, для полиморфных связей: `October\Rain\Database\MorphPivot`.
**pivotSortable** | указывает столбец порядка сортировки для сводной таблицы, используется в сочетании с [трейтом модели](../lists/structures.md) `SortableRelation`.
**pivotKey** | указывает автоинкрементный столбец ID для сводной таблицы, должен использоваться с пользовательским классом `pivotModel` с первичным ключом, используемым в таблице.

<a id="relation-has-many-through"></a>
### Has Many Through

Связь has-many-through предоставляет удобный способ доступа к удалённым связям через промежуточную связь. Например, модель `Country` может иметь много моделей `Post` через промежуточную модель `User`. В этом примере вы можете легко собрать все записи блога для данной страны. Рассмотрим таблицы, необходимые для определения этой связи:

```
countries
    id - integer
    name - string

users
    id - integer
    country_id - integer
    name - string

posts
    id - integer
    user_id - integer
    title - string
```

Хотя `posts` не содержит столбца `country_id`, связь `hasManyThrough` предоставляет доступ к постам страны через `$country->posts`. Для выполнения этого запроса модель проверяет `country_id` в промежуточной таблице `users`. После нахождения совпадающих ID пользователей они используются для запроса таблицы `posts`.

Теперь, когда мы изучили структуру таблицы для связи, определим её в модели `Country`:

```php
class Country extends Model
{
    public $hasManyThrough = [
        'posts' => [
            \Acme\Blog\Models\Post::class,
            'through' => \Acme\Blog\Models\User::class
        ],
    ];
}
```

Первый аргумент, передаваемый в связь `$hasManyThrough` — это имя финальной модели, к которой мы хотим получить доступ, а параметр `through` — это имя промежуточной модели.

Стандартные соглашения о внешних ключах будут использоваться при выполнении запросов связи. Если вы хотите настроить ключи связи, вы можете передать их как параметры `key`, `otherKey` и `throughKey` в определение `$hasManyThrough`. Параметр `key` — это имя внешнего ключа в промежуточной модели, параметр `throughKey` — это имя внешнего ключа в финальной модели, а `otherKey` — это локальный ключ.

```php
public $hasManyThrough = [
    'posts' => [
        \Acme\Blog\Models\Post::class,
        'key' => 'my_country_id',
        'through' => \Acme\Blog\Models\User::class,
        'throughKey' => 'my_user_id',
        'otherKey' => 'my_id',
        'secondOtherKey' => 'my_country_id'
    ],
];
```

<a id="relation-has-one-through"></a>
### Has One Through

Связь has-one-through связывает модели через одну промежуточную связь. Например, если у каждого поставщика есть один пользователь, и у каждого пользователя есть одна запись истории, то модель поставщика может получить доступ к истории пользователя через пользователя. Рассмотрим таблицы базы данных, необходимые для определения этой связи:

```
users
    id - integer
    supplier_id - integer

suppliers
    id - integer

history
    id - integer
    user_id - integer
```

Хотя таблица `history` не содержит столбца `supplier_id`, связь `hasOneThrough` может предоставить доступ к истории пользователя модели поставщика. Теперь, когда мы изучили структуру таблицы для связи, определим её в модели `Supplier`:

```php
class Supplier extends Model
{
    public $hasOneThrough = [
        'userHistory' => [
            \Acme\Supplies\Model\History::class,
            'through' => \Acme\Supplies\Model\User::class
        ],
    ];
}
```

Первый параметр массива, передаваемый в свойство `$hasOneThrough` — это имя финальной модели, к которой мы хотим получить доступ, а ключ `through` — это имя промежуточной модели.

Стандартные соглашения о внешних ключах будут использоваться при выполнении запросов связи. Если вы хотите настроить ключи связи, вы можете передать их как параметры `key`, `otherKey` и `throughKey` в определение `$hasManyThrough`. Параметр `key` — это имя внешнего ключа в промежуточной модели, параметр `throughKey` — это имя внешнего ключа в финальной модели, а `otherKey` — это локальный ключ.

```php
public $hasOneThrough = [
    'userHistory' => [
        \Acme\Supplies\Model\History::class,
        'key' => 'supplier_id',
        'through' => \Acme\Supplies\Model\User::class,
        'throughKey' => 'user_id',
        'otherKey' => 'id',
        'secondOtherKey' => 'my_country_id'
    ],
];
```

<a id="relation-polymorphic-relations"></a>
## Полиморфные связи

Полиморфные связи позволяют модели принадлежать более чем одной другой модели в рамках одной ассоциации.

### Полиморфная связь один к одному

#### Структура таблицы

Полиморфная связь один к одному похожа на простую связь один к одному; однако целевая модель может принадлежать более чем одному типу модели в рамках одной ассоциации. Например, представьте, что вы хотите хранить фотографии для ваших сотрудников и для ваших продуктов. Используя полиморфные связи, вы можете использовать одну таблицу `photos` для обоих этих сценариев. Сначала рассмотрим структуру таблицы, необходимую для построения этой связи:

```
staff
    id - integer
    name - string

products
    id - integer
    price - integer

photos
    id - integer
    path - string
    imageable_id - integer
    imageable_type - string
```

Два важных столбца — это `imageable_id` и `imageable_type` в таблице `photos`. Столбец `imageable_id` будет содержать значение ID владеющего сотрудника или продукта, а столбец `imageable_type` будет содержать имя класса владеющей модели. Столбец `imageable_type` — это то, как ORM определяет, какой «тип» владеющей модели возвращать при доступе к связи `imageable`.

#### Структура модели

Далее рассмотрим определения модели, необходимые для построения этой связи:

```php
class Photo extends Model
{
    public $morphTo = [
        'imageable' => []
    ];
}

class Staff extends Model
{
    public $morphOne = [
        'photo' => [\Acme\Blog\Models\Photo::class, 'name' => 'imageable']
    ];
}

class Product extends Model
{
    public $morphOne = [
        'photo' => [\Acme\Blog\Models\Photo::class, 'name' => 'imageable']
    ];
}
```

#### Получение полиморфных связей

После определения таблицы базы данных и моделей вы можете получить доступ к связям через свои модели. Например, для доступа к фотографии сотрудника мы можем просто использовать динамическое свойство `photo`:

```php
$staff = Staff::find(1);

$photo = $staff->photo
```

Вы также можете получить владельца полиморфной связи из полиморфной модели, обращаясь к имени связи `morphTo`. В нашем случае это определение `imageable` в модели `Photo`. Таким образом, мы будем обращаться к нему как к динамическому свойству:

```php
$photo = Photo::find(1);

$imageable = $photo->imageable;
```

Связь `imageable` модели `Photo` вернёт либо экземпляр `Staff`, либо `Product`, в зависимости от того, какому типу модели принадлежит фотография.

### Полиморфная связь один ко многим

#### Структура таблицы

Полиморфная связь один ко многим похожа на простую связь один ко многим; однако целевая модель может принадлежать более чем одному типу модели в рамках одной ассоциации. Например, представьте, что пользователи вашего приложения могут «комментировать» как посты, так и видео. Используя полиморфные связи, вы можете использовать одну таблицу `comments` для обоих этих сценариев. Сначала рассмотрим структуру таблицы, необходимую для построения этой связи:

```
posts
    id - integer
    title - string
    body - text

videos
    id - integer
    title - string
    url - string

comments
    id - integer
    body - text
    commentable_id - integer
    commentable_type - string
```

#### Структура модели

Далее рассмотрим определения модели, необходимые для построения этой связи:

```php
class Comment extends Model
{
    public $morphTo = [
        'commentable' => []
    ];
}

class Post extends Model
{
    public $morphMany = [
        'comments' => [\Acme\Blog\Models\Comment::class, 'name' => 'commentable']
    ];
}

class Product extends Model
{
    public $morphMany = [
        'comments' => [\Acme\Blog\Models\Comment::class, 'name' => 'commentable']
    ];
}
```

#### Получение связи

После определения таблицы базы данных и моделей вы можете получить доступ к связям через свои модели. Например, для доступа ко всем комментариям поста мы можем использовать динамическое свойство `comments`:

```php
$post = Author\Plugin\Models\Post::find(1);

foreach ($post->comments as $comment) {
    //
}
```

Вы также можете получить владельца полиморфной связи из полиморфной модели, обращаясь к имени связи `morphTo`. В нашем случае это определение `commentable` в модели `Comment`. Таким образом, мы будем обращаться к нему как к динамическому свойству:

```php
$comment = Author\Plugin\Models\Comment::find(1);

$commentable = $comment->commentable;
```

Связь `commentable` модели `Comment` вернёт либо экземпляр `Post`, либо `Video`, в зависимости от того, какому типу модели принадлежит комментарий.

Вы также можете обновить владельца связанной модели, установив атрибут с именем связи `morphTo`, в данном случае `commentable`.

```php
$comment = Author\Plugin\Models\Comment::find(1);
$video = Author\Plugin\Models\Video::find(1);

$comment->commentable = $video;
$comment->save()
```

### Полиморфная связь многие ко многим

#### Структура таблицы

В дополнение к связям «один к одному» и «один ко многим» вы также можете определить полиморфные связи «многие ко многим». Например, модели блога `Post` и `Video` могут разделять полиморфную связь с моделью `Tag`. Использование полиморфной связи многие ко многим позволяет иметь единый список уникальных тегов, которые разделяются между записями блога и видео. Сначала рассмотрим структуру таблицы:

```
posts
    id - integer
    name - string

videos
    id - integer
    name - string

tags
    id - integer
    name - string

taggables
    tag_id - integer
    taggable_id - integer
    taggable_type - string
```

#### Структура модели

Далее мы готовы определить связи в модели. Модели `Post` и `Video` обе будут иметь связь `tags`, определённую в свойстве `$morphToMany` базового класса модели:

```php
class Post extends Model
{
    public $morphToMany = [
        'tags' => [\Acme\Blog\Models\Tag::class, 'name' => 'taggable']
    ];
}
```

#### Определение обратной связи

Далее, в модели `Tag` вы должны определить связь для каждой из связанных моделей. Таким образом, для этого примера мы определим связь `posts` и связь `videos`:

```php
class Tag extends Model
{
    public $morphedByMany = [
        'posts'  => [\Acme\Blog\Models\Post::class, 'name' => 'taggable'],
        'videos' => [\Acme\Blog\Models\Video::class, 'name' => 'taggable']
    ];
}
```

#### Получение связи

После определения таблицы базы данных и моделей вы можете получить доступ к связям через свои модели. Например, для доступа ко всем тегам поста вы можете просто использовать динамическое свойство `tags`:

```php
$post = Post::find(1);

foreach ($post->tags as $tag) {
    //
}
```

Вы также можете получить владельца полиморфной связи из полиморфной модели, обращаясь к имени связи, определённой в свойстве `$morphedByMany`. В нашем случае это методы `posts` или `videos` в модели `Tag`. Таким образом, вы будете обращаться к этим связям как к динамическим свойствам:

```php
$tag = Tag::find(1);

foreach ($tag->videos as $video) {
    //
}
```

#### Пользовательские полиморфные типы

По умолчанию полное имя класса используется для хранения типа связанной модели. Например, в приведённом выше примере, где `Photo` может принадлежать `Staff` или `Product`, значение `imageable_type` по умолчанию будет либо `Acme\Blog\Models\Staff`, либо `Acme\Blog\Models\Product` соответственно.

Использование пользовательского полиморфного типа позволяет отвязать вашу базу данных от внутренней структуры приложения. Вы можете определить «карту морфов» связи для предоставления пользовательского имени для каждой модели вместо имени класса:

```php
use October\Rain\Database\Relations\Relation;

Relation::morphMap([
    'staff' => \Acme\Blog\Models\Staff::class,
    'product' => \Acme\Blog\Models\Product::class,
]);
```

Наиболее распространённое место для регистрации `morphMap` — метод `boot` [файла регистрации плагина](../extending.md).

<a id="oc-querying-relations"></a>
## Запросы к связям

Поскольку все типы связей модели могут быть вызваны как функции, вы можете вызывать эти функции для получения экземпляра связи без фактического выполнения запросов связи. Кроме того, все типы связей также служат [конструкторами запросов](./query.md), позволяя вам продолжать добавлять ограничения к запросу связи перед окончательным выполнением SQL в вашей базе данных.

Например, представьте систему блога, в которой модель `User` имеет много связанных моделей `Post`:

```php
class User extends Model
{
    public $hasMany = [
        'posts' => \Acme\Blog\Models\Post::class
    ];
}
```

### Доступ через метод связи

Вы можете запросить связь **posts** и добавить дополнительные ограничения к связи, используя метод `posts`. Это даёт вам возможность использовать любые методы [конструктора запросов](./query.md) для связи.

```php
$user = User::find(1);

$posts = $user->posts()->where('is_active', 1)->get();

$post = $user->posts()->first();
```

### Доступ через динамическое свойство

Если вам не нужно добавлять дополнительные ограничения к запросу связи, вы можете просто обращаться к связи, как если бы она была свойством. Например, продолжая использовать наши примеры моделей `User` и `Post`, мы можем получить доступ ко всем постам пользователя, используя свойство `$user->posts`.

```php
$user = User::find(1);

foreach ($user->posts as $post) {
    // ...
}
```

Динамические свойства используют «ленивую загрузку», что означает, что данные связи загружаются только при фактическом доступе к ним. Из-за этого разработчики часто используют жадную загрузку (см. ниже) для предварительной загрузки связей, которые, как они знают, будут использованы после загрузки модели. Жадная загрузка значительно уменьшает количество SQL-запросов, которые необходимо выполнить для загрузки связей модели.

### Запросы существования связи

При доступе к записям модели вы можете захотеть ограничить результаты на основе существования связи. Например, представьте, что вы хотите получить все записи блога, которые имеют хотя бы один комментарий. Для этого вы можете передать имя связи методу `has`:

```php
// Retrieve all posts that have at least one comment...
$posts = Post::has('comments')->get();
```

Вы также можете указать оператор и количество для дополнительной настройки запроса:

```php
// Retrieve all posts that have three or more comments...
$posts = Post::has('comments', '>=', 3)->get();
```

Вложенные операторы `has` также могут быть построены с использованием «точечной» нотации. Например, вы можете получить все посты, которые имеют хотя бы один комментарий и голос:

```php
// Retrieve all posts that have at least one comment with votes...
$posts = Post::has('comments.votes')->get();
```

Если вам нужно ещё больше возможностей, вы можете использовать методы `whereHas` и `orWhereHas` для добавления условий «where» к вашим запросам `has`. Эти методы позволяют добавлять пользовательские ограничения к ограничению связи, например проверку содержимого комментария:

```php
// Retrieve all posts with at least one comment containing words like foo%
$posts = Post::whereHas('comments', function ($query) {
    $query->where('content', 'like', 'foo%');
})->get();
```

#### Встроенные запросы существования связи

Для запроса существования связи с одним условием к запросу связи удобнее использовать методы `whereRelation`, `orWhereRelation`, `whereMorphRelation` или `orWhereMorphRelation`.

```php
$posts = Post::whereRelation('comments', 'is_approved', false)->get();
```

Методы `searchWhereRelation` или `orSearchWhereRelation` доступны для поиска по столбцам связи. Подобно [поисковым запросам](./query.md), метод добавит к запросу, используя поисковый термин (первый аргумент), имя связи (второй аргумент) и столбцы поиска (третий аргумент), используя нечувствительный к регистру запрос LIKE.

```php
$posts = Post::searchWhereRelation('foo bar', 'author', ['name', 'bio'])->get();
```

#### Запросы отсутствия связи

Вы можете передать имя связи методам `doesntHave` и `orDoesntHave` для ограничения результатов на основе отсутствия связи.

```php
$posts = Post::doesntHave('comments')->get();
```

Методы `whereDoesntHave` и `orWhereDoesntHave` могут добавлять дополнительные ограничения запроса к вашим запросам `doesntHave`.

```php
$posts = Post::whereDoesntHave('comments', function ($query) {
    $query->where('content', 'like', 'code%');
})->get();
```

### Подсчёт связанных записей

В некоторых сценариях вы можете захотеть подсчитать количество связанных записей, найденных в данном определении связи. Метод `withCount` может использоваться для включения столбца `{relation}_count` с выбранными моделями.

```php
$users = User::withCount('roles')->get();

foreach ($users as $user) {
    echo $user->roles_count;
}
```

Метод `withCount` поддерживает несколько связей вместе с дополнительными ограничениями запроса.

```php
$posts = Post::withCount(['votes', 'comments' => function ($query) {
    $query->where('content', 'like', 'foo%');
}])->get();

echo $posts[0]->votes_count;
echo $posts[0]->comments_count;
```

Вы можете лениво загрузить столбец подсчёта с помощью метода `loadCount`.

```php
$user = User::first();
$user->loadCount('roles');
```

Дополнительные ограничения запроса также поддерживаются.

```php
$user->loadCount(['roles' => function ($query) {
    $query->where('clearance', '>', 5);
}])
```

## Жадная загрузка

При доступе к связям как к свойствам данные связи загружаются «лениво». Это означает, что данные связи фактически не загружаются, пока вы впервые не обратитесь к свойству. Однако модели могут «жадно» загружать связи во время запроса родительской модели. Жадная загрузка устраняет проблему N + 1 запросов. Чтобы проиллюстрировать проблему N + 1 запросов, рассмотрим модель `Book`, связанную с `Author`.

```php
class Book extends Model
{
    public $belongsTo = [
        'author' => \Acme\Blog\Models\Author::class
    ];
}
```

Теперь давайте получим все книги и их авторов:

```php
$books = Book::all();

foreach ($books as $book) {
    echo $book->author->name;
}
```

Этот цикл выполнит 1 запрос для получения всех книг из таблицы, затем ещё один запрос для каждой книги для получения автора. Таким образом, если у нас 25 книг, этот цикл выполнит 26 запросов: 1 для исходной книги и 25 дополнительных запросов для получения автора каждой книги.

К счастью, мы можем использовать жадную загрузку для сокращения этой операции до всего 2 запросов. При запросе вы можете указать, какие связи должны быть жадно загружены, используя метод `with`:

```php
$books = Book::with('author')->get();

foreach ($books as $book) {
    echo $book->author->name;
}
```

Для этой операции будут выполнены только два запроса:

```sql
select * from books

select * from authors where id in (1, 2, 3, 4, 5, ...)
```

#### Жадная загрузка нескольких связей

Иногда вам может потребоваться жадно загрузить несколько различных связей в одной операции. Для этого просто передайте дополнительные аргументы методу `with`:

```php
$books = Book::with('author', 'publisher')->get();
```

#### Вложенная жадная загрузка

Для жадной загрузки вложенных связей вы можете использовать «точечную» нотацию. Например, давайте жадно загрузим всех авторов книги и все личные контакты автора в одном выражении:

```php
$books = Book::with('author.contacts')->get();
```

### Ограничение жадной загрузки

Иногда вы можете захотеть жадно загрузить связь, но также указать дополнительные ограничения запроса для жадной загрузки. Вот пример:

```php
$users = User::with([
    'posts' => function ($query) {
        $query->where('title', 'like', '%first%');
    }
])->get();
```

В этом примере модель будет жадно загружать только те посты, у которых столбец `title` содержит слово `first`. Конечно, вы можете вызывать другие методы [конструктора запросов](./query.md) для дополнительной настройки операции жадной загрузки:

```php
$users = User::with([
    'posts' => function ($query) {
        $query->orderBy('created_at', 'desc');
    }
])->get();
```

### Ленивая жадная загрузка

Иногда вам может потребоваться жадно загрузить связь после того, как родительская модель уже была получена. Например, это может быть полезно, если вам нужно динамически решить, загружать ли связанные модели:

```php
$books = Book::all();

if ($someCondition) {
    $books->load('author', 'publisher');
}
```

Если вам нужно установить дополнительные ограничения запроса для жадной загрузки, вы можете передать `Closure` методу `load`:

```php
$books->load([
    'author' => function ($query) {
        $query->orderBy('published_date', 'asc');
    }
]);
```

## Вставка связанных моделей

Как и при запросе связи, October CMS поддерживает определение связи с использованием подхода метода или динамического свойства. Например, возможно, вам нужно вставить новый `Comment` для модели `Post`. Вместо ручной установки атрибута `post_id` в `Comment` вы можете вставить `Comment` непосредственно из связи.

### Вставка через метод связи

October CMS предоставляет удобные методы для добавления новых моделей к связям. В основном модели могут быть добавлены к связи или удалены из связи. В каждом случае связь соответственно ассоциируется или диссоциируется.

#### Метод Add

Используйте метод `add` для ассоциации новой связи.

```php
$comment = new Comment(['message' => 'A new comment.']);

$post = Post::find(1);

$comment = $post->comments()->add($comment);
```

Обратите внимание, что мы не обращались к связи `comments` как к динамическому свойству. Вместо этого мы вызвали метод `comments` для получения экземпляра связи. Метод `add` автоматически добавит соответствующее значение `post_id` к новой модели `Comment`.

Если вам нужно сохранить несколько связанных моделей, вы можете использовать метод `addMany`:

```php
$post = Post::find(1);

$post->comments()->addMany([
    new Comment(['message' => 'A new comment.']),
    new Comment(['message' => 'Another comment.']),
]);
```

#### Метод Remove

Для сравнения, метод `remove` может использоваться для диссоциации связи, делая запись осиротевшей.

```php
$post->comments()->remove($comment);
```

В случае связей многие ко многим запись удаляется из коллекции связи.

```php
$post->categories()->remove($category);
```

В случае связи «belongs to» вы можете использовать метод `dissociate`, который не требует передачи связанной модели.

```php
$post->author()->dissociate();
```

#### Добавление с данными сводной таблицы

При работе со связью многие ко многим метод `add` принимает массив дополнительных атрибутов промежуточной «сводной» таблицы в качестве второго аргумента.

```php
$user = User::find(1);

$pivotData = ['expires' => $expires];

$user->roles()->add($role, $pivotData);
```

Второй аргумент метода `add` также может указывать ключ сессии, используемый отложенной привязкой, при передаче в виде строки. В этих случаях данные сводной таблицы могут быть переданы как третий аргумент.

```php
$user->roles()->add($role, $sessionKey, $pivotData);
```

#### Метод Create

Хотя `add` и `addMany` принимают полный экземпляр модели, вы также можете использовать метод `create`, который принимает PHP-массив атрибутов, создаёт модель и вставляет её в базу данных.

```php
$post = Post::find(1);

$comment = $post->comments()->create([
    'message' => 'A new comment.',
]);
```

Перед использованием метода `create` обязательно ознакомьтесь с документацией по [массовому присваиванию](./model.md) атрибутов, так как атрибуты в PHP-массиве ограничены определением «fillable» модели.

### Вставка через динамическое свойство

Связи могут быть установлены напрямую через их свойства так же, как вы бы обращались к ним. Установка связи этим способом перезапишет любую связь, существовавшую ранее. Модель должна быть сохранена после этого, как и с любым атрибутом.

```php
$post->author = $author;

$post->comments = [$comment1, $comment2];

$post->save();
```

Альтернативно вы можете установить связь, используя первичный ключ, что полезно при работе с HTML-формами.

```php
// Assign to author with ID of 3
$post->author = 3;

// Assign comments with IDs of 1, 2 and 3
$post->comments = [1, 2, 3];

$post->save();
```

Связи могут быть диссоциированы путём присвоения значения NULL свойству.

```php
$post->author = null;

$post->comments = null;

$post->save();
```

Подобно отложенной привязке, связи, определённые для несуществующих моделей, откладываются в памяти до их сохранения. В этом примере пост ещё не существует, поэтому атрибут `post_id` не может быть установлен в комментарии через `$post->comments`. Поэтому ассоциация откладывается до создания поста путём вызова метода `save`.

```php
$comment = Comment::find(1);

$post = new Post;

$post->comments = [$comment];

$post->save();
```

### Связи многие ко многим

#### Присоединение / Отсоединение

При работе со связями многие ко многим модели предоставляют несколько дополнительных вспомогательных методов для более удобной работы со связанными моделями. Например, представьте, что пользователь может иметь много ролей, а роль может иметь много пользователей. Для присоединения роли к пользователю путём вставки записи в промежуточную таблицу, объединяющую модели, используйте метод `attach`:

```php
$user = User::find(1);

$user->roles()->attach($roleId);
```

При присоединении связи к модели вы также можете передать массив дополнительных данных для вставки в промежуточную таблицу:

```php
$user->roles()->attach($roleId, ['expires' => $expires]);
```

Конечно, иногда может потребоваться удалить роль у пользователя. Для удаления записи связи многие ко многим используйте метод `detach`. Метод `detach` удалит соответствующую запись из промежуточной таблицы; однако обе модели останутся в базе данных:

```php
// Detach a single role from the user...
$user->roles()->detach($roleId);

// Detach all roles from the user...
$user->roles()->detach();
```

Для удобства `attach` и `detach` также принимают массивы ID в качестве входных данных:

```php
$user = User::find(1);

$user->roles()->detach([1, 2, 3]);

$user->roles()->attach([1 => ['expires' => $expires], 2, 3]);
```

#### Синхронизация

Вы также можете использовать метод `sync` для построения ассоциаций многие ко многим. Метод `sync` принимает массив ID для размещения в промежуточной таблице. Любые ID, которые не находятся в данном массиве, будут удалены из промежуточной таблицы. Таким образом, после завершения этой операции только ID из массива будут существовать в промежуточной таблице:

```php
$user->roles()->sync([1, 2, 3]);
```

Вы также можете передать дополнительные значения промежуточной таблицы вместе с ID:

```php
$user->roles()->sync([1 => ['expires' => true], 2, 3]);
```

### Обновление временных меток родителя

Когда модель `belongsTo` или `belongsToMany` другой модели, например `Comment`, принадлежащий `Post`, иногда полезно обновить временную метку родителя при обновлении дочерней модели. Например, при обновлении модели `Comment` вы можете захотеть автоматически «коснуться» временной метки `updated_at` владеющего `Post`. Просто добавьте свойство `touches`, содержащее имена связей, в дочернюю модель:

```php
class Comment extends Model
{
    /**
     * All of the relationships to be touched.
     */
    protected $touches = ['post'];

    /**
     * Relations
     */
    public $belongsTo = [
        'post' => \Acme\Blog\Models\Post::class
    ];
}
```

Теперь при обновлении `Comment` владеющий `Post` также обновит свой столбец `updated_at`:

```php
$comment = Comment::find(1);

$comment->text = 'Edit to this comment!';

$comment->save();
```

## Отложенная привязка

Отложенная привязка позволяет вам отложить привязку связей модели до момента, когда основная запись зафиксирует изменения. Это особенно полезно, если вам нужно подготовить некоторые модели (такие как загрузка файлов) и ассоциировать их с другой моделью, которая ещё не существует.

Вы можете отложить любое количество **подчинённых** моделей относительно **основной** модели, используя **ключ сессии**. Когда основная запись сохраняется вместе с ключом сессии, связи с подчинёнными записями автоматически обновляются для вас. Отложенная привязка поддерживается в [поведении Форм](../backend/form.md) панели управления автоматически, но вы можете захотеть использовать эту функцию в других местах.

### Генерация ключа сессии

Ключ сессии необходим для отложенной привязки. Вы можете представить ключ сессии как идентификатор транзакции. Один и тот же ключ сессии должен использоваться для привязки/отвязки связей и сохранения основной модели. Вы можете сгенерировать ключ сессии с помощью PHP-функции `uniqid()`. Обратите внимание, что [хелпер формы](../../markup/function/form.md) автоматически генерирует скрытое поле, содержащее ключ сессии.

```php
$sessionKey = uniqid('session_key', true);
```

### Отложить привязку связи

Комментарий в следующем примере не будет добавлен к посту, если пост не будет сохранён.

```php
$comment = new Comment;
$comment->content = "Hello world!";
$comment->save();

$post = new Post;
$post->comments()->add($comment, $sessionKey);
```

::: tip
Объект `$post` не был сохранён, но связь будет создана, если сохранение произойдёт.
:::

### Отложить отвязку связи

Комментарий в следующем примере не будет удалён, если пост не будет сохранён.

```php
$comment = Comment::find(1);
$post = Post::find(1);
$post->comments()->remove($comment, $sessionKey);
```

### Список всех привязок

Используйте метод `withDeferred` связи для загрузки всех записей, включая отложенные. Результаты также будут включать существующие связи.

```php
$post->comments()->withDeferred($sessionKey)->get();
```

### Отмена всех привязок

Рекомендуется отменить отложенную привязку и удалить подчинённые объекты, а не оставлять их осиротевшими.

```php
$post->cancelDeferred($sessionKey);
```

### Фиксация всех привязок

Вы можете зафиксировать (привязать или отвязать) все отложенные привязки при сохранении основной модели, предоставив ключ сессии вторым аргументом метода `save`.

```php
$post = new Post;
$post->title = "First blog post";
$post->save(['sessionKey' => $sessionKey]);
```

Тот же подход работает с методом `create` модели:

```php
$post = Post::create(['title' => 'First blog post'], $sessionKey);
```

### Ленивая фиксация привязок

Если вы не можете предоставить `$sessionKey` при сохранении, вы можете зафиксировать привязки в любое время с помощью следующего кода:

```php
$post->commitDeferred($sessionKey);
```

### Очистка осиротевших привязок

Уничтожает все привязки, которые не были зафиксированы и старше 1 дня:

```php
October\Rain\Database\Models\DeferredBinding::cleanUp(1);
```

::: tip
October CMS автоматически уничтожает отложенные привязки старше 5 дней с помощью сборки мусора.
:::

### Отключение отложенной привязки

Иногда вам может потребоваться полностью отключить отложенную привязку для данной модели, например, если вы загружаете её из отдельного подключения к базе данных. Для этого вам нужно убедиться, что свойство `sessionKey` модели равно `null` до выполнения хуков предварительной и последующей отложенной привязки во внутреннем методе сохранения. Для этого вы можете привязаться к событию `model.saveInternal` модели.

```php
public function __construct()
{
    parent::__construct(...func_get_args());

    $this->bindEvent('model.saveInternal', function () {
        $this->sessionKey = null;
    });
}
```

::: tip
Это полностью отключит отложенную привязку для любых моделей, к которым вы применяете это переопределение.
:::
