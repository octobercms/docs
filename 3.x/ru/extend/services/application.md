# Приложение

Контейнер инверсии управления (IoC) — это инструмент для управления зависимостями классов. Внедрение зависимостей — это метод устранения жёстко закодированных зависимостей классов. Вместо этого зависимости внедряются во время выполнения, что обеспечивает большую гибкость, поскольку реализации зависимостей можно легко заменять.

#### Привязка к контейнеру

Существует два способа разрешения зависимостей контейнером IoC: через callback-функции Closure и автоматическое разрешение. Сначала рассмотрим callback-функции Closure. Сначала «тип» может быть привязан к контейнеру.

```php
App::bind('foo', function($app) {
    return new FooBar;
});
```

#### Разрешение из контейнера

```php
$value = App::make('foo');
```

Когда вызывается метод `App::make`, выполняется callback-функция Closure и возвращается результат.

#### Привязка «общего» типа к контейнеру

Иногда вы можете захотеть привязать что-то к контейнеру, что должно быть разрешено только один раз, и тот же экземпляр должен возвращаться при последующих вызовах контейнера:

```php
App::singleton('foo', function() {
    return new FooBar;
});
```

#### Привязка существующего экземпляра к контейнеру

Вы также можете привязать существующий экземпляр объекта к контейнеру с помощью метода `instance`:

```php
$foo = new Foo;

App::instance('foo', $foo);
```

#### Привязка интерфейса к реализации

В некоторых случаях класс может зависеть от реализации интерфейса, а не от «конкретного типа». В этом случае необходимо использовать метод `App::bind`, чтобы сообщить контейнеру, какую реализацию интерфейса следует внедрить:

```php
App::bind('UserRepositoryInterface', 'DbUserRepository');
```

Теперь рассмотрим следующий код:

```php
$users = App::make('UserRepositoryInterface');
```

Поскольку мы привязали `UserRepositoryInterface` к конкретному типу, `DbUserRepository` будет автоматически внедрён в этот контроллер при его создании.

### Где регистрировать привязки

Привязки IoC, как и [обработчики событий](./event.md), обычно относятся к категории «загрузочного кода». Другими словами, они подготавливают ваше приложение к обработке запросов и обычно должны выполняться до фактического вызова маршрута или контроллера. Наиболее распространённое место — метод `boot` [файла регистрации плагина](../extending.md). Альтернативно плагины могут предоставить файл с именем **init.php** в директории плагина, который вы можете использовать для размещения логики регистрации IoC.

## Поставщики сервисов

Поставщики сервисов — это отличный способ создания библиотек и выполнения связанных регистраций IoC в одном месте. В поставщике сервиса вы можете зарегистрировать пользовательский драйвер аутентификации, зарегистрировать классы репозиториев вашего приложения в контейнере IoC или даже настроить пользовательскую команду Artisan.

Фактически [файлы регистрации плагинов](../system/plugins.md) наследуют поставщики сервисов, и большинство основных компонентов включают поставщики сервисов. Все зарегистрированные поставщики сервисов для вашего приложения перечислены в массиве `providers` конфигурационного файла `config/app.php`.

#### Определение поставщика сервиса

Для создания поставщика сервиса просто расширьте класс `October\Rain\Support\ServiceProvider` и определите метод `register`:

```php
use October\Rain\Support\ServiceProvider;

class FooServiceProvider extends ServiceProvider
{
    public function register()
    {
        $this->app->bind('foo', function() {
            return new Foo;
        });
    }
}
```

Обратите внимание, что в методе `register` контейнер IoC приложения доступен через свойство `$this->app`. После создания провайдера и готовности к его регистрации в вашем приложении просто добавьте его в массив `providers` в конфигурационном файле `app`.

#### Регистрация поставщика сервиса во время выполнения

Вы также можете зарегистрировать поставщик сервиса во время выполнения с помощью метода `App::register`.

```php
App::register('FooServiceProvider');
```

## События приложения

#### События запроса

Вы можете зарегистрировать специальные события перед маршрутизацией запроса с помощью методов `before` и `after`.

```php
App::before(function ($request) {
    // Code to execute before the request is routed
});

App::after(function ($request) {
    // Code to execute after the request is routed
});
```

#### События контейнера

Сервис-контейнер генерирует событие каждый раз, когда он разрешает объект. Вы можете слушать это событие с помощью метода `resolving`.

```php
App::resolving(function ($object, $app) {
    // Called when container resolves object of any type...
});

App::resolving('foo', function ($fooBar, $app) {
    // Called when container resolves objects using hint "foo"...
});

App::resolving('Acme\Blog\Classes\FooBar', function ($fooBar, $app) {
    // Called when container resolves objects of type "FooBar"...
});
```

Как видите, разрешаемый объект передаётся в callback, позволяя вам установить любые дополнительные свойства объекта перед его передачей потребителю.

## Вспомогательные методы приложения

#### Определение окружения приложения

Вы можете использовать метод `environment` для определения окружения приложения, как оно настроено в [конфигурации окружения](../../setup/configuration.md).

```php
// production
App::environment();
```

#### Определение контекста выполнения

Можно узнать, выполняется ли текущий запрос в административной области панели управления, с помощью метода `runningInBackend`.

```php
App::runningInBackend();
```

Вы также можете использовать метод `runningInConsole`, чтобы проверить, выполняется ли код в [интерфейсе командной строки](../console-commands.md):

```php
App::runningInConsole();
```
